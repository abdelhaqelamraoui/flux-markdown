# Change: 为报错界面提供一键反馈和自动诊断

## Why

用户的两点要求是产品验收标准：报错必须指导用户继续完成任务；反馈必须从现场一次点击发起，并由软件准备已知信息。上一版方案强调了覆盖和诊断，却保留了必经的本地编辑窗口，且缺少明确的补救优先级。本次重审将正常路径简化为“看懂下一步 → 直接补救，或一键发起反馈”。

## What Changes

- 统一报错表达：“什么任务未完成”＋一至两句可执行指导。主按钮执行推荐补救，次要操作为“反馈此问题”，保留安全关闭；详细步骤和技术信息按需展开。
- 错误现场的默认反馈路径为：一次点击“反馈此问题”→ 自动准备并保留报告 → 直接打开已预填的 GitHub 表单。无需寻找帮助菜单、复制日志、选择已知错误类别或先经过本地报告编辑窗口。
- 问题类别、错误摘要、应用/系统版本、相关设置和诊断由软件填写；补充说明与最小样例可选，诊断缺失不会阻止反馈。提供适用于自动反馈的 Issue 表单，避免现有必填下拉框要求用户重复填写。
- 反馈按钮旁简短说明接收方和附带数据；展开后可以检查/编辑/排除诊断。打开预填网址时数据即交给 GitHub，最终公开发布由用户在 GitHub 确认。应用不能将“打开表单”显示为“反馈已发送”。
- 在展示报错前冻结本次事件的上下文；使用公共恢复动作、反馈路由和有界诊断模块，所有报错点复用，避免各自拼文案、读取日志或生成网址。
- 覆盖主应用、Quick Look、本机错误提示和 Web 渲染器；局部错误保持行内展示，重复故障合并。渲染器未加载时原生反馈入口仍可用。
- 浏览器、网络或跨进程交接失败时保留当前报告，在同一处提供重试/复制/保存，不递归弹窗。自动诊断默认排除文档正文、搜索词、私人路径、凭据和原始系统日志。
- 五种语言、键盘与辅助功能纳入验收；CLI 给出补救和反馈路径而不自动打开 GUI。将以上原则写为 AGENTS.md 的长期规则。

## Impact

- Affected specs: 新增 `error-feedback`；复用已批准实现的 `add-feedback-diagnostics` 和现有 `project-support`，不改变现有设置历史保留策略。
- Affected code: `Sources/Shared/FeedbackDiagnostics.swift`、新的错误上下文/诊断存储、`FeedbackView.swift`、`AppUpdaterController.swift`、自动反馈 Issue 表单、主应用文件/渲染/导出路径、Quick Look 控制器及受控启动代理、Web 渲染器错误展示和桥接、五套本地化、用户文档与相关测试。
- 默认复用 GitHub，不新增服务端或 GitHub Token；仅在用户点击反馈后向其传递经过过滤的预填内容。GitHub 登录/最终发布是明确的外部步骤；若用户要求点击即发送并获得接收回执，需要另行明确反馈接收服务，不能用“打开草稿”冒充已发送。
- 覆盖清单、数据模型、跨进程交接、降级方式和验收边界见 `design.md`。
- 操作系统/其他程序生成的窗口、扩展未被调用时的 Finder 回退、进程崩溃后不存在的错误窗口无法直接添加按钮；对此保留主应用帮助菜单/下次启动反馈与可验证诊断，不承诺捕获从未执行的代码或追溯旧版本事件。

## Review status

已按用户再次强调的两点要求完成设计重审与规范修订。默认采用现有 GitHub 渠道的一键直达路径；用户尚未批准功能实施，本轮不将设计修改视为实施批准。
